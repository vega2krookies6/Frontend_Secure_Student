# 00. 프론트엔드 보안 가이드 — React SPA 작성 시 고려사항

> OWASP Top 10 2025 참고 카테고리: **#1 접근 제어 실패**, **#4 암호화 실패**, **#5 인젝션(XSS)**, **#9 보안 로깅 및 모니터링 실패**
> 대상: `student_detail_department_react` (React 19 + Vite + react-router-dom + zustand + axios)
> 함께 보면 좋은 문서: `docs/API_SPEC.md`(이 앱이 호출하는 API 계약), 백엔드 `Student_JWT/docs/security/00~10`(브랜치별 보안 실습)

## 1. 왜 프론트엔드에도 보안 문서가 필요한가

백엔드 실습 문서들은 "공격 → 서버가 어떻게 막는가"를 다룬다. 이 문서는 반대편, **브라우저에서 실행되는 코드**를 다룬다.

전제는 하나다 — **브라우저에 도착한 모든 것은 이미 사용자(공격자)의 손 안에 있다.**

- 자바스크립트 소스는 `F12` 개발자 도구로 전부 읽을 수 있다. 난독화해도 실행 가능한 형태로 내려가는 한 완전히 숨길 수 없다.
- `fetch`/axios 요청은 그대로 가로채거나 변형해서 다시 보낼 수 있다(Burp Suite, 브라우저 개발자 도구 모두 가능).
- `sessionStorage`/`localStorage`/쿠키 등 브라우저에 저장한 값은 그 브라우저를 쓰는 사람이 전부 읽고 바꿀 수 있다.

따라서 프론트엔드 코드로 할 수 있는 일은 **"못 하게 막기"가 아니라 "하지 않도록 안내하기(UX)"** 뿐이다. 실제 차단은 반드시 서버가 한다. 이 원칙이 아래 모든 항목의 기준이 된다.

---

## 2. 핵심 원칙 — 신뢰 경계(Trust Boundary)는 서버다

| 할 수 있는 일 (프론트엔드) | 할 수 없는 일 (프론트엔드) |
|---|---|
| 역할에 맞는 화면/메뉴를 보여주거나 숨긴다 | 권한 검사를 "대신"한다 |
| 입력값을 서버에 보내기 전에 미리 걸러 사용자 경험을 개선한다 | 입력값 검증을 서버 대신 "최종" 판단한다 |
| 서버가 돌려준 403/404를 그대로 보여준다 | 서버 응답 없이 "이 사람은 접근 가능/불가능"을 스스로 판정한다 |

이 프로젝트에서 실제로 이 원칙을 따른 예:

- `src/App.jsx` — 학생 등록/수정 라우트는 `AdminOnly`로 막지 않는다. "본인 것인가"는 서버만 알기 때문에, 화면은 누구나 들어오게 둔 뒤 서버가 403을 주면 그 메시지를 보여준다.

  ```jsx
  // App.jsx — 소유권처럼 서버에 물어야만 아는 경우에는 AdminOnly를 쓰지 않는다
  <Route path="/students/:id/edit" element={<RequireAuth><StudentFormPage /></RequireAuth>} />
  ```

- `src/pages/StudentFormPage.jsx` — 조회·저장이 403으로 실패하면 서버 메시지를 그대로 보여주고 목록으로 돌려보낸다. 프론트엔드가 "이 사람은 못 본다"를 미리 계산하지 않는다.
- `src/pages/StudentListPage.jsx` / `src/components/MyStudentLookup.jsx` — `isAdmin` 여부로 **화면만** 다르게 보여줄 뿐, 실제 데이터 접근 권한은 매 요청마다 서버가 다시 판정한다(`GET /api/students/number/{studentNumber}`가 소유자가 아니면 403).

> 역할 기반 UI 분기(`isAdmin ? A : B`)는 편의를 위한 것이며 보안 장치가 아니라는 점을 분명히 인지해야 한다. 분기 조건을 조작해 화면을 강제로 띄워도, 서버가 403을 돌려주면 데이터는 보이지 않는다.

## 3. OWASP Top 10 관점에서 본 고려사항

### 3-1. #4 암호화 실패 — 토큰을 어디에 보관하는가

| 저장 위치 | 새로고침 | 탭 닫기 | XSS 노출 시 |
|---|---|---|---|
| 메모리(변수/상태) | 사라짐 | 사라짐 | 짧게만 노출 |
| `sessionStorage` | 유지 | 사라짐 | 탭이 열린 동안만 노출 |
| `localStorage` | 유지 | 유지 | **영구적으로** 노출(탭을 닫아도 유효) |

이 앱은 `sessionStorage`를 쓴다(`src/lib/token.js`). `localStorage`보다 노출 기간이 짧다는 점에서 `localStorage`보다는 낫지만, XSS가 터지면 세션이 열려 있는 동안 토큰을 그대로 읽어갈 수 있다는 한계는 동일하다. 실무에서 가장 안전한 방법은 토큰을 JS가 전혀 읽을 수 없는 **HttpOnly 쿠키**에 담는 것이지만, 이 프로젝트는 교육 목적상 "직접 토큰을 다루며 흐름을 이해하는 것"을 우선해 `sessionStorage` + Bearer 헤더 방식을 유지한다. → 그래서 3-2의 XSS 차단이 더 중요해진다.

```js
// src/lib/token.js
export const getToken = () => sessionStorage.getItem(TOKEN_KEY);
export const setToken = (token) => sessionStorage.setItem(TOKEN_KEY, token);
```

### 3-2. #5 인젝션 — XSS (Cross-Site Scripting)

React는 JSX에 넣은 값(`{value}`)을 기본적으로 **문자열로 escape**해서 렌더링한다. `<script>`를 변수에 넣어 화면에 출력해도 태그로 해석되지 않고 글자 그대로 보인다. 그래서 "평범한 JSX만 쓰는" 코드는 XSS에 상당히 안전하다.

이 보호가 깨지는 지점은 단 하나, **`dangerouslySetInnerHTML`을 쓰거나 DOM에 직접 `innerHTML`을 대입할 때**다. 이 프로젝트에는 두 가지 모두 없다(`src/` 전체 검색으로 확인됨). 앞으로 기능을 추가할 때도 이 둘은 쓰지 않는 것이 원칙이다 — 꼭 HTML을 그려야 한다면 신뢰할 수 없는 입력은 반드시 DOMPurify 같은 라이브러리로 정제한 뒤에만 넣는다.

### 3-3. #1 접근 제어 실패 — CSRF는 왜 이 앱에서 상대적으로 덜 위험한가

CSRF는 "브라우저가 쿠키를 자동으로 실어 보낸다"는 점을 악용한다. 이 앱은 로그인 유지에 쿠키를 쓰지 않고, 토큰을 **직접 `Authorization: Bearer ...` 헤더**에 담아 보낸다(`src/api/client.js`). 공격 사이트가 `<form>` 자동 제출이나 `<img src="...">`로 요청을 흘려보내도, 그 요청에는 피해자의 토큰이 실리지 않는다 — 브라우저가 자동으로 붙여주는 건 쿠키뿐이지 sessionStorage 값이 아니기 때문이다. 그래서 Bearer 토큰 방식의 SPA는 CSRF에 비교적 안전하지만, "비교적"일 뿐 XSS가 뚫리면 토큰 자체를 훔쳐 가므로 3-2의 방어가 여전히 핵심이다.

### 3-4. #9 보안 로깅 및 모니터링 실패 — 민감정보를 콘솔/에러에 남기지 않는다

이 앱의 모든 catch 블록은 `console.error("Error:", error)` 형태로 통일되어 있다(`authStore.js`, `studentStore.js`, `MyStudentLookup.jsx` 등). 에러 객체 자체를 그대로 찍을 뿐, 비밀번호나 토큰 값을 별도로 `console.log`하는 코드는 없다. 브라우저 콘솔은 개발자 도구를 열면 누구나 볼 수 있고, 운영 환경에서도 그대로 남기 때문에 다음을 지킨다.

- 비밀번호·토큰·주민번호류 값은 어떤 이유로도 `console.log`하지 않는다.
- 에러 메시지에 서버가 준 문구 이상의 내부 정보(쿼리, 스택트레이스 전체 등)를 덧붙이지 않는다.

## 4. 프론트엔드 작성 시 하지 말아야 할 것 — 체크리스트

| 금지 사항 | 이유 |
|---|---|
| 비밀번호·API 키·토큰을 소스코드에 하드코딩 | 빌드 결과(JS 번들)에 그대로 들어가 누구나 볼 수 있고, git에 한 번 올라가면 기록에 영구히 남는다 |
| `dangerouslySetInnerHTML` / `innerHTML` 직접 대입 | React의 기본 XSS 방어(자동 escape)를 스스로 해제하는 것과 같다 |
| 권한 검사를 프론트엔드 로직만으로 끝내기 | 개발자 도구로 조건을 우회하면 그대로 뚫린다 — 서버가 다시 검사해야 한다(2장) |
| `localStorage`에 토큰·개인정보를 기본값으로 저장 | 탭을 닫아도 남아, XSS 노출 시간이 가장 길다 |
| 민감정보를 `console.log`로 남기기 | 운영 환경 콘솔에도 그대로 남아 누구나 열어볼 수 있다 |
| `.env` 값에 "비밀"을 담고 빌드하기 (`VITE_` 접두사 변수 등) | Vite의 `VITE_*` 환경변수는 **빌드 시점에 번들 안에 문자열로 그대로 박힌다**. 서버만 알아야 할 비밀(API 시크릿 키 등)은 여기 두면 안 되고, 서버 주소처럼 "공개되어도 되는 값"만 둔다 |
| 서버 응답(403/404)을 무시하고 프론트엔드가 가진 캐시/상태를 그대로 믿기 | 삭제되었거나 권한이 바뀐 데이터를 화면에 계속 보여주게 된다 |
| alert/confirm 결과만으로 삭제 등 민감 동작을 확정 | 사용자 확인용 UX일 뿐, 실제 삭제 권한은 서버가 다시 검사해야 한다(이 앱은 `DELETE`를 관리자 전용으로 서버에서 막아 둔다) |

## 5. 이 프로젝트가 실제로 적용한 방어

- **토큰 자동 만료 처리** — `src/api/client.js`가 401을 받으면 `refreshToken`으로 한 번 조용히 갱신해 보고, 그래도 실패하면 토큰을 모두 지우고 로그인 화면으로 보낸다(`notifyExpired()` → `App.jsx`가 듣고 처리).
- **동시 요청 중복 갱신 방지** — 화면을 열자마자 여러 API를 한꺼번에 부를 때, 갱신 요청이 여러 번 나가 `refreshToken` 회전 구조와 충돌하지 않도록 `refreshingPromise`로 한 번만 갱신하게 묶었다.
- **역할 기반 UI는 보여주기용, 실제 차단은 서버** — 2장에서 설명한 대로 `StudentListPage`/`MyStudentLookup`/`StudentFormPage` 모두 서버의 403 응답을 그대로 신뢰한다.
- **테스트 계정 비밀번호를 코드에 적지 않음** — `src/pages/LoginPage.jsx`는 계정 목록을 `API_SPEC.md`로만 안내하고, 비밀번호를 화면 문구나 주석에 적지 않는다.

## 6. 백엔드의 보안 취약점 데모 코드는 반영하지 않는다

백엔드(`Student_JWT`)의 `vuln.*` 패키지들(SQLi, XSS, IDOR, CSRF, 역직렬화 등)은 "취약한 상태"를 의도적으로 남겨 공격을 실습하기 위한 코드다. 이 React 앱은 Student/Department를 다루는 **정상 동작 화면**이고, 백엔드의 취약점 데모는 전혀 다른 도메인(User/Voucher)과 별도 API(`/api/vuln/**`)로 격리되어 있어 이 앱이 호출할 일이 없다. 따라서 그 취약 코드를 프론트엔드에 옮기거나 흉내 낼 필요가 없으며, 이 앱은 처음부터 끝까지 "안전한 버전"만 유지한다.
